## Safety (out-of-process plug-ins): verification and default-on decision
- Real OS input on the owner's 14-plug-in library (generated project, nothing of theirs committed): every editor opens, takes clicks and typing, sends edits back and marks the project edited; Space and ⌘S work after clicking in an editor; save, quit and reopen restore every parameter.
- Found and fixed with tests:
  - An isolated editor stayed on the Space where its host first drew it: "visible" but off screen. The panel now joins every Space (full-screen auxiliary too). The window server briefly reports the panel mid-appear-animation (476 × 350), so the editor test polls up to 1 s for its size.
  - Opening AUSampler's editor isolated aborted its host: `fit()` resized the window, the layout changed the view's frame, the frame-change notification re-entered `fit()` until AppKit's subview counter overflowed. Now re-entry queues one pass and a burst cap stops oscillation. AUSampler's view autoresizes in width only, so each resize grew it by the old mismatch (3,937 pt); it now keeps its requested size (1186 × 596).
  - Opening a real project in-process showed Edited: a VST3 sampler reported values through performEdit and later a changed state through setDirty after its background load, with no editor open. VST3, then AU (listener events) and CLAP (mark_dirty, gesture/value output events) now count only while the editor is open. The CLAP fixture gained a minimal editor so its tests open it; the closed-editor cases are new tests.
  - Isolated load: one activate call blocked the main thread for 1.2 s. Sampling showed a single `sendto` waiting: macOS ignores MSG_DONTWAIT on this AF_UNIX socket pair (a 10-line C test confirms it blocks; O_NONBLOCK returns EAGAIN). The descriptor is non-blocking while sending, at most 2 ms per call. Test with 3 × 4 MB states: 984 → 6.3 ms.
  - A host killed during playback marked the project edited; failures no longer count as edits.
- `dalnok-cli load-bench` opens projects as the app does. On 24 of the owner's Logic projects (APFS clones, imported to scratch): isolated loading never blocks more than 16 ms in 23 (in-process ≈1 s), faster in 20. But 7 projects whose plug-ins cost more than 40 % of a block in series miss 29–97 % of blocks isolated. **Decision: Safety stays opt-in**; the next A-01 step is concurrent processing of isolated plug-ins on independent tracks (ADR-0014 amendment with the numbers and a migration note).
- Stress: 64 isolated instances (2.5 s load, 22.6 MB/host, ≈54 µs/instance/block), 10 open/close cycles of a 33-plug-in project (no leaks, never edited), host killed mid-play (contained).

## Safety on by default (later the same day)
- Parallel processing landed (commit 128e4bd), but after it p6, p7 and p9 still missed blocks. Tracing each block showed bursts about 0.4 s into play. The host's own timing put the cause in one sampler: its script, resumed after a wait, does about 36 ms of work on the audio thread. In-process `load-bench` never saw it because the benchmark slept between blocks. With the main run loop turning, as the app runs, in-process playback stalls 70–124 ms at that point. `load-bench` now runs the run loop.
- Fixes:
  - Hosts process 0.75 s of silence before answering (live only). That cured p7's first-block skips; the test fixture's one-off stall goes from 3 missed blocks to 0.
  - p7's 56–132 ms load call was `commit()`. Snapshot compiles asked every isolated host for its latency over the socket, waiting on that host's main thread, which was busy right after loading. Latency is now in the shared block, published by the host before hello, after every control request, and after editor edits. It is not on a timer: asking some plug-ins for latency takes a lock their audio thread also takes. Automation ranges are cached per instance. Worst load call 132 → 2 ms.
  - The fixtures (VST3 crash/hang counter, CLAP editor edits) count only blocks with signal, so the warm-up doesn't trigger them.
- One run with the load average at 5–14 (other work on the machine) showed 10 projects missing blocks. An interleaved A/B against the previous commit showed no regression. That load sensitivity is written into ADR-0014 as a known limit.
- Final: 24 projects, worst isolated load call ≤13 ms, faster in 23, no isolated block over the period, 22 with no misses. Safety on by default; an explicit off is kept.

## FL-style clip motion
- `ClipMotion.swift`:
  - A dragged clip lifts (scale 1.045, shadow) and follows the pointer on a 120 Hz spring, leaning with its speed. A dashed ghost marks the snapped landing place.
  - On drop, it glides onto the ghost with a squash.
  - Clips that appear pop in; deleted ones poof.
- The pictures are drawn with the timeline's own clip drawing into a transparent bitmap, so a multi-clip lift has no lanes behind it. Opening another project doesn't animate.
- The self-test covers lift, follow, scale, drop, settle, pop, poof, cleanup and Reduce Motion.

## Owner feedback on clip motion (before the 0.2.0 release)
- Bug: after moving a clip, a frozen copy stayed on screen while scrolling, and the real clip wasn't redrawn. `endLift` handed the drop to a local `ClipLift` whose completion block held it weakly; when the timeline let go, the block never removed the picture or cleared `lifted`. The self-test held the lift strongly, which hid this. It now holds it weakly and checks that no picture is left over.
- More grid snapping: the lifted clip springs to its snapped landing place (grid step and lane) instead of following the pointer.
- Settings ▸ Appearance ▸ Clip bounce (0–100 %, default 65 %; 50 % is the first tuning) scales the lift, follow spring, lean, squash and pop.
