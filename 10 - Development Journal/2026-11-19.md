## A-08 deferred plug-in activation
- Plug-in creation can't move off the main thread (CLAP create/init and VST3 setup are main-thread calls; many AUs assume it), so ADR-0013 keeps it there and splits apply instead: the model goes live with every slot queued, then the app activates one per run-loop turn.
- Engine: `ApplyMode::{load, recover, defer}`, a FIFO of queued slot ids, `activateNextPlugin` (skips removed or already-loaded slots, times the init, commits), `cancelPendingPlugins`, `reloadPlugin`. UI-visible changes from loading bump the revision without marking the project edited. C API 32 adds `dalnok_project_apply_deferred`, `dalnok_plugins_pending/activate_next/cancel_pending`, `dalnok_plugin_reload` and `DalnokPluginSlotInfo.loading`.
- App: open and import use deferred apply; `Session.activatePendingPlugins` sleeps 1 ms between plug-ins so the window draws and Stop is handled. The status line shows "Loading plug-ins n of N…" with a Stop button; the track menu offers Load for unloaded slots (also useful after recovery). The device panel and mixer now rebuild when a slot's loaded state or message changes; before, a plug-in that loaded later would have kept its "not loaded" view.
- First test run found the fixture's in-memory media wasn't saved with the project (silence); switched to a WAV on disk. The first self-test run showed "Opening…" over the progress line; progress now replaces the transient message.
- `DeferredActivation` (3 tests) and the self-test's deferred-loading checks pass; Graphite self-test 533 checks.

## A-01 stage 1: out-of-process plug-in hosting
- ADR-0014. `dalnok-plughost` (tools/dalnok-plughost, a C main calling `dalnok_plughost_main`) is built from the engine library, so the VST3/CLAP/AU hosts run unchanged inside it. One process per instance; built-in plug-ins stay in-process.
- Audio: one shared-memory block per instance (inputs, outputs, sidechain, notes, block-rate automation) with `request`/`done` counters, woken through `os_sync_wake_by_address_any`/`os_sync_wait_on_address(_with_timeout)` in shared mode (macOS 14.4+; older systems spin). The engine's audio thread waits at most 40 % of the block period (offline: 10 s), passes dry/silent when late, and never re-requests while the host is busy, so the host never reads a buffer being rewritten. The wake/wait is the declared `-Wfunction-effects` exception, like the plug-in call itself. The host's processing thread uses a time-constraint policy.
- Control: length-prefixed requests over a socket pair (5 s timeout), served on the host's main thread from a CFFileDescriptor run-loop source. The host `_exit`s when the socket closes.
- Failure: `poll()` (from `collectGarbage`) reaps a dead host or kills one that missed ~2 s of deadlines; the slot reports the reason (`loaded = false`, error with "Load restarts it"); offline renders skip failed instances, matching what is heard; `reloadPlugin` replaces a failed instance from saved state.
- Opt-in: `DALNOK_PLUGIN_HOST` (engine default, for tests/CLI) and Settings ▸ Plug-ins ▸ Safety in the app (`Engine.isolatePlugins`, host binary next to the app; `scripts/bundle.sh` copies it).
- Testing found two app-killing bugs before they shipped: writing to a crashed host's socket raised SIGPIPE in the engine process (now `SO_NOSIGPIPE`), and the crash path called `exitReason()` twice, so the second call (after reaping) recorded an empty failure that read as "loaded".
- Evidence: `scripts/ci/plugin-isolation.sh` — PluginHosting, DelayCompensation and ClapHosting all pass with every plug-in isolated (17 tests; two editor assertions now expect no editor when isolated), and PluginIsolation (bit-exact null against in-process; crash mid-session reported, project intact, reload restores processing; hang bounded per block and reported; crash/hang while loading fail only the load). Release overhead with the test gain VST3: in-process 1.2/2.2/4.2 µs p50, isolated 33.6/34.3/34.7 µs p50 (p99 ≈ 47 µs) at 64/128/256 frames. Self-test: Safety routes new plug-ins to the host and an Apple AUDelay loads isolated (Graphite 538).
- Not done: editors out of process, default-on after a pass over the owner's plug-in library, a per-callback deadline budget shared across isolated plug-ins, audio-workgroup membership for the host thread.

## A-01 stage 2, item 3: shared deadline and audio workgroup
- Measured first: a new test with three isolated plug-ins that hang in the same block, followed by a healthy one. On the old code the worst callback took 13.06–13.09 ms of a 10.67 ms period, because each hung plug-in waited its own 40 %. (After the onset block, busy hosts are skipped instantly, so only the onset block overruns.)
- Engine::process stamps `Scratch::deadlineNs` = start + 40 % of the callback period. The renderer hands it to every plug-in (`setDeadline`, non-virtual). A remote plug-in waits only until that deadline; once it has passed, it skips without a request and counts `budgetSkips_`, not a miss. After the change: worst 4.46–4.54 ms. After 3.2 s the hung plug-ins are reported "stopped responding" and the healthy one is not. `nowNs` in plugin_remote is now marked nonblocking (commpage read, suppression as in engine.cpp); `rt-effects.sh` is clean.
- Workgroup: a prototype (AudioWorkInterval in a parent, registered port, `os_workgroup_create_with_port` in the child) joined with result 0, so it is feasible. Design: registered rendezvous port at spawn; the host replies with its own port. `AudioDevice::workgroupPort()` (CoreAudio: `kAudioDevicePropertyIOThreadOSWorkgroup` of the running device, including the default-output unit's current device and the duplex device). `Engine::updateWorkgroup()` runs after device start, stop, capture start and capture stop, and sends the port to every isolated instance (and to new ones). The host's listener thread publishes it, and the processing thread leaves and joins before its next block.
- Bugs found on the way: `MACH_MSG_TIMEOUT_NONE` is 0, so a "don't wait" receive blocked forever (the test hung; sampled and fixed). The weak-imported SPI resolved to null in the engine link (now `dlsym`). `mach_port_insert_right` was given a right type instead of a disposition. Releasing the send right before `posix_spawn` made spawn fail with EINVAL. When registration was off, the host sent its reply to a port inherited from the test runner, so the host now answers only with `--rendezvous`.
- Evidence: `hostThreadJoinsTheDeviceWorkgroup` (real output device, skipped on CI): host started before the device joined with join = 0, joins = 1; host started while the device runs also joined; after stop and start, joins = 2. `plugin-isolation.sh` (17 + 12), `rt-effects.sh` clean, 218 engine tests.
- Housekeeping: `ps` showed orphaned `swiftpm-testing-helper` processes hung in the init-hang fixture (one from this session's `plugin-recovery.sh` run, others 6–18 h old). The recovery script's hang case appears to leave its test process behind. Killed the one from this session; not investigated further.
- Sanitizers: PluginIsolation, DeferredActivation and PluginHosting (25 tests) pass under AddressSanitizer. Under ThreadSanitizer there are no race reports, but the budget test's tight timing bound (60 % of the period) failed at TSan speed: p50 1.52 ms, max 9.26 ms, still under the period. The test now always asserts no overrun and applies the tight bound only when p50 < 1 ms.

## A-03: structural undo as clip deltas
- Before (release `audit-bench` with the generated 16 × 256 project, `--edits 500`; I added an RSS line after the structural-edit loop): 34.4 → 303.3 MB (0.54 MB per edit). Edit p50 0.274 ms, undo p50 0.27–0.28 ms.
- Design: the top of each stack stays a full snapshot. When another step is pushed above it, it is compacted against the state it will next be applied to. For the undo stack that is the pre-edit state; for redo it is the state before the undo. The compacted form is the model without clips, plus changed clips, plus the clip order if it changed (`ModelDelta`). Applying a step rebuilds the clips from the live model. This works because a step is only ever applied to exactly that base state, as traced through edits, scalar steps, groups, undo and redo.
- Test `UndoDeltas.randomHistoryReproducesEveryState`, 3 seeds: 120 recorded states, then a full undo walk, a full redo walk, and a branch, comparing the serialized project at every step. The first run failed on the unchanged engine too, because a nudge clamped at zero returns OK without recording a step. The test now counts a step only when the model revision changes.
- First version: edit p50 0.48 ms, from an extra model copy and a hash map per edit. Now it compacts against `before` and then moves it, and compares clips by index with a lazily built map. After: RSS growth 3.3–3.4 MB (about 80×), edit p50 0.298–0.300 ms, undo p50 0.358–0.373 ms. 219 engine tests pass; undo suites pass under ASan.
