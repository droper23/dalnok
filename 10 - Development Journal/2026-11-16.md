## Decisions (owner Q&A)

## Research
Steinberg relicensed the VST3 SDK to MIT in Oct 2025, which makes a permissive, independent engine
practical. JUCE is AGPLv3 or commercial. Tracktion Engine is GPLv3 or commercial and needs a JUCE
license too. Audacity 4.0 (Sep 2026) is a Qt6 rewrite without MIDI or a mixer. See [[Foundation Evaluation]].

## Problems hit
- The macOS SDK declares `AURenderCallback` with the real-time effect, so our callback chain had to be

- Apple clang 21 has no `-fsanitize=realtime`. RealtimeSanitizer is planned via Homebrew LLVM.
- One round-trip test failure was a test bug: the signal reached −1.006 full scale, which integer formats correctly clip.

## Tests

### CI crash after M4 (fixed)

**test-only** use-after-free: the relink test released a media handle and then passed it to the API
again. Fixed, and a `sanitizers` CI job (ASan + TSan) now runs on every push, so this class of bug
fails deterministically. The engine itself was clean under both sanitizers, and so was the app self-test under ASan.

## Capture buffer and Scarlett channels
Added a preallocated SPSC interleaved capture buffer with all-or-nothing blocks and dropped-frame accounting. Native tests cover empty/full, oversize, wraparound, and 200,000 ordered stereo frames across two threads; normal and ThreadSanitizer runs pass. The buffer is not yet connected to hardware or a writer. A separate short AVFoundation capture reported identical very low peaks (-63 dBFS) on channels 1 and 2 and silence on 3 and 4; it does not prove an active microphone signal.

A later short Scarlett capture peaked at -29.2 dBFS on channels 1 and 2. Subtracting those channels gave digital silence: the capture path may duplicate one input, so this is not proof that the hardware inputs are independently working. Channels 3 and 4 were silent. Temporary audio was deleted.

## Capture writer foundation
Added an off-thread drain with independent overflow, write, and finalization error flags and frame counters. A temporary PCM spool creates files exclusively, flushes its header and final data, and permits read-only inspection of complete and partial frames. Native tests cover normal drain, overflow, injected write/finalize errors (including combined errors), file contents, no-overwrite, malformed headers, partial tails, and a write failure. Normal and ThreadSanitizer runs pass. These pieces are not connected to a device, model, UI, final audio file, or crash recovery; Phase 2 remains incomplete.

A separate process-kill test confirms the spool header and complete frames can be inspected after a writer process is killed before finalization; it does not simulate power loss or recover an actual project. A deterministic synthetic ten-second stereo capture preserved its frame count and checked sample values. Native normal, AddressSanitizer, and ThreadSanitizer runs pass.

A C API v5 snapshot operation writes a project copy without marking it saved or changing its revision. The persistence test verifies exact offline-render output after reload and preserves dirty state on success and I/O failure. All 66 engine tests pass. Automatic scheduling, recovery selection, and full Phase 2 remain unimplemented.

## M8: recording and MIDI integration (evening session)
**Built.** Recording sessions in the engine (`record.cpp`): one armed audio track and/or one armed instrument
track, a journal per take, finalization (spool → float WAV by atomic link, folder fsync, read-back check), and
placement as one undo step with latency compensation. The take starts at the first audio block in which the
transport advances; the audio thread marks a take broken if the transport stops or jumps. A simulated duplex
device (`DALNOK_SIMULATED_INPUT`, `dalnok_engine_pump_input`) runs the real callback path in tests. MIDI: notes on
clips (shared immutable lists, so undo copies stay cheap), instrument tracks, Dalnok Poly (PolyBLEP saw, two-pole
low-pass, linear ADSR, 16 voices), constant tempo and meter, quantize, Core MIDI input ports (UMP MIDI 1.0 words
fed into the existing parser), live play-through on the armed instrument, and MIDI recording. App: R chips, input
buttons, record button, menus, recovery, MIDI clip drawing. Phase 4 start: read-only plugin discovery and ADR-0009.

**Verified.** `swift test`: 90 tests. Mutation checks: removing latency compensation fails the recording tests;
a 442 Hz tuning error fails the pitch test (after tightening its tolerance from 0.5% to ±0.5 Hz, because the first
version let it through). `scripts/ci/record-crash.sh`: SIGKILL at 0.05, 0.7 and 2.5 s; every recovered sample
exact; spool unchanged by repeated recovery. Scarlett Solo 4th Gen at 44.1 kHz: 10 s and 120 s takes through
`dalnok-cli record`, 0 dropped frames (5,292,032 frames = 120.0 s). Hardware capture test under TSan passed
(it had been interrupted last session). TSan on the recording and MIDI suites is clean. RT effect analysis clean.
GUI self-test 154 checks in both themes. Release build clean.

**Problems hit.**
- The Core MIDI receive block must itself be `nonblocking` (the SDK annotates it) and blocks can't be `noexcept`,
  so the noexcept-implication warning is suppressed for that block only.
- TSan reported a race between the parser's constructor (control thread) and the receive thread, because the
  only ordering came from inside Core MIDI. The parser is now published through an atomic slot that the receive
  block reads with acquire.
- The self-test's prefix menu matcher picked "Record Enable Track" for "Record"; it now supports exact titles.

**Not done / honest limits.** Latency compensation uses device-reported figures (1,186 frames on the Solo) and
has not been measured with a loopback cable. Monitoring was not checked by ear. No power-loss test. The MiniLab
was not played into a recording this session. MIDI timing is block-accurate. No piano roll editor, tempo map,
metronome, or plugin loading.

## M9: piano roll, bars and beats, metronome, motion (continued session)
**Built.** `scripts/make-test-project.sh` (+ `dalnok-cli make-test-project`, `TestProject.swift`) generates five
deterministic presets from synthesized audio and MIDI; it immediately found a header bug (long names squeezed the
chips). Bars-and-beats ruler/grid/snap/LCD with tempo and meter in the control bar. Metronome on the audio thread

**Verified.** 92 tests; Metronome tests check the click lands on the exact beat sample, accent 1.6 kHz vs 1 kHz,
silent offline. GUI self-test 185 checks in both themes, including synthesized piano-roll gestures and motion checks
(knob glide after undo, record pulse, palette fade, and instant behavior with motion reduced). RT effects and TSan
clean.

**Problems hit.** (1) The tempo field became first responder at launch and silently disabled every single-key
shortcut; found because the self-test's Delete check failed. A launch check now guards it. (2) An honest-check slip:
I first wrote a metronome check ending in `|| true`; replaced it with a real measurement past the session end.
(3) Edit ▸ Delete deleted the timeline clip while the piano roll was in use under the self-test (app inactive, so
`isKeyWindow` was false); focus is now tracked explicitly.

**M10–M11 (plugins).** Vendored the MIT VST3 interfaces and CLAP headers. `dalnok-scan` validates one plugin per
process; fake crashing, hanging, noisy and codeless plugins are contained and classified. VST3 hosting runs
instruments and inserts in-process with state persistence. Two real bugs found by the tests: SwiftPM had been
compiling the fixture plugins into the scanner binary, and adding an insert changed a mono track's pan law (so
even a passthrough was not transparent). The real-time checker rejected a temporary `RenderTrack` on the audio
thread (its destructor could free memory). Vital renders notes offline when hosted.

**M12 (editors and parameters).** Controller creation (single component or separate, connected both ways), a
component handler forwarding editor edits, fixed-capacity parameter changes on the audio thread, IPlugView in an
NSView with resize. Two self-test failures were test bugs (a menu item's menu is weak; a stale "first item"
assumption). AppKit's view cache cannot capture GPU-drawn editors, so the editor check uses `screencapture -l`.

**Not verified.** Animations were checked by state and by still frames, not by watching them; nobody has judged
their feel. The piano roll has no marquee selection or keyboard-only note entry.

## Import timing and sequence identity
REAPER imports preserve constant tempo and meter and Ableton imports preserve constant tempo. Logic sequence rows are keyed by row and channel identity, and events before any sequence do not inherit later row names. Generated import tests cover these cases. Further validation of Logic sequence and take-folder semantics remains necessary.

## MIDI timing and split continuity
Constant tempo edits now scale MIDI clips and notes to preserve beat placement; audio stays fixed in time. Offline rendering caught a pre-existing split bug: notes crossing adjacent MIDI pieces were cut off. Shared note sources now allow continuous playback and persist in project format v3. Tests cover timing, rollback on overflow, split/reopen rendering and Core MIDI; full `scripts/check.sh` passed. Older project files lack shared-source identity, and frame rounding remains until a beat-based tempo-map model is implemented.

## Self-test reliability
Guarded several track/control array accesses and removed a narrow UI tick timing assumption in the gain ring check; deterministic endpoint timing includes a small clock-rounding margin. GUI self-test passed in both themes. The earlier intermittent index crash was not reproduced and remains unconfirmed.

## Logic malformed-input handling
A generated fixture with duplicate primary region IDs confirms the importer leaves ambiguous placements unresolved instead of choosing arbitrary audio. Another fixture verifies truncated known event records fail import. LogicImport tests pass.

## MIDI source corruption regression
Generated malformed version 3 shared-note data is rejected transactionally; offline audio remains identical after the failed load.
